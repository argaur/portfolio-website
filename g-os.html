Eight systems, each stating its purpose and its method in one place. This tab answers what exists; the Playbook tab answers when each piece fires.

Purpose

Turn a raw idea into a PRD.md that survives scrutiny — before the depth dial is scored. The rubric requires a PRD and cites it for every answer, so writing it can't live inside the spine it feeds. /prd-create is a 6-stage state machine that produces PRD.md with a Provenance block, which /rubric then requires and cites for each of its 5 answers.

Operating rules — apply to every stage
Gaurav owns the problemClaude never invents or assumes the idea, pain point, or problem statement — only surfaces, refines, and pressure-tests what Gaurav gives it.
2–3 options, alwaysEvery decision point offers real alternatives with tradeoffs. Never a single unilateral call.
Research stays separatePRIMARY_RESEARCH.md and SECONDARY_RESEARCH.md are never merged, and never folded into the PRD as first-draft prose — the PRD cites them.
Broad before narrowNever assume a problem statement and research backward to justify it. Divergence happens before any research question is written, and those questions are git-committed before narrowing is allowed — so the answer can't be reverse-engineered from the desired conclusion.
Process
A Spark→ B Diverge→ ◆ git-lock→ C Research→ D Narrow→ E Draft→ F Seal
A
Spark
Gaurav dumps the raw idea in whatever form it comes, captured near-verbatim into SPARK.md. Claude asks clarifying questions one at a time — never reframes or narrows. Everything defaults to hypothesis confidence.
B
Problem-space map / Diverge
≥3 distinct problem framings, including one mandatory anti-thesis framing — the version where this isn't worth solving, or the pain is adjacent. Gaurav does not pick yet; the output is a research agenda, not a decision. Gate: "Framings approved."
C
Research — bias lock
Questions are derived from all Stage B framings and committed to git before any narrowing is allowed — the actual lock, not an honor system. Primary and secondary research are never merged. PRIMARY_RESEARCH.md holds interview scripts and transcripts (no confidence tag anywhere without a quotable line here); SECONDARY_RESEARCH.md holds the market scan as a Steal List. Both require an Evidence Against section with ≥3 entries, or an explicit "found nothing" log. Fast path for experiment mode — a PRD drafted with only the template's optional low-stakes section filled — is a ~30-min secondary-only sweep instead of the full cycle. An all-hypothesis result is the expected shape there, not a failure.
D
Narrow
Problem clustering → P1→P2→P3→core-failure chain → 2–3 candidate statements, each with supporting and contradicting evidence cited by file anchor, plus "what evidence would flip this." Gaurav finalizes the wording; Claude only builds the evidence dossier. Gate: "Problem statement finalized."
E
Template select + draft
Stakes × type choose which of the one template's optional sections apply. Every claim carries a confidence tag plus a reference into the research files — the PRD cites research, it doesn't restate it. Every success criterion is rewritten into falsifiable form, and the Prior Art & Steal List carries forward to Blueprint P0.
F
Grill + seal
grill-me targets the discovery chain specifically: "which Stage B framing did the research actually kill?" If the answer is "none," that's surfaced as a smell, not silently passed. Survivors seal into PRD.md with a Provenance block — template used, stakes classification, research refs, grill date. Gate: "PRD approved" → /rubric.

One template, every cell. Documentation/templates/PRD.template.md, 483 lines — tap a cell to read it raw. Purpose

The rigorous track, for anything with real consequences — auth, payments, 3+ entities, real users, portfolio-grade builds. /rubric requires PRD.md to exist and cites it for every answer — it refuses to run on a vacuum idea.

Method

Eight phases (P0–P7), each ending in an explicit gate. No auto-advance — Gaurav approves every transition. This is the only spine; every project runs it. /rubric does not choose a framework, it sets the depth dial: 2+ yes runs full depth, 0–1 runs a lean pass with fewer artifacts. Same phases, same gates, either way.

Expand → P1
Hold → P2–P3
Reduce → P4
Phase detail
P0
PRD Intake
Read PRD → 5-bullet read-back → falsifiable success criteria → ambiguity list → Prior Art steal list. Steelman gate: state the polarizing claim, give the sharpest counter in two sentences, defend in two. If the defense doesn't hold, revisit scope before P1. Provenance short-circuit: if the PRD already carries a Provenance block, steps 2–5 are read from it rather than regenerated — P0 becomes a confirmation gate, not a repeat. Gate: "Read-back approved."
P1
Solution Stage
POT-format interview (Proposal → Options → Tell me). Eight topics in order: core journey, MVP features, non-goals, tech shape, third-party services, metrics, recruiter signal, risk register. One session, max 10 questions. Gate: "Solution approved."
P2
Design
Hands off to the 7-stage Design Framework (§03). Required artifact from Stage 1: Named Reader — one specific real person this product must land for, stored in brand-guide.md. Gate: "Spec approved."
P3
Implementation Plan
Slice 0 is the walking skeleton: frontend shell + /health + DB + PostHog + Sentry + docs stub. Remaining slices ordered by risk; each is one capability plus tests, analytics, and a HOW_TO_USE section. model-router runs before the gate, so every step carries a model tag. Gate: "Plan approved."
P4
Development
Per slice: Red (failing tests, mandatory — no skipping to Green) → Green → Refactor → Instrument → Document → Review → Smoke-run → Commit. Between slices: a 5-line PROGRESS.md update. Context compaction is harness-managed now, not a manual step. Gate: all tests green, HOW_TO_USE complete.
P5
Testing
Layer 0 security (IDOR, one user reaching another user's data by guessing an ID; authz; input sanitization) · Layer 1 unit + integration + E2E · Layer 2 the 8-category edge-case checklist · Layer 3 acceptance criteria. Gate: CI green, zero P0/P1 bugs, acceptance criteria walked.
P6
Deployment
13 items: env vars, secrets, /health, migrations, PostHog, Sentry, HTTPS, CORS, rate limits, backups, CI, README, CASE_STUDY.md. Post-deploy: a Playwright smoke test against the live URL — light/dark/mobile screenshots, zero console errors, zero failed requests. Gate: Definition of Shipped, 7 conditions confirmed.
P7
Postmortem
Added 2026-08-01, and it exists because of a specific hole: success criteria were being authored in every PRD and then never scored against reality. Entry condition is real, not "when you feel like it" — the PRD's shortest success-criterion timeframe has elapsed since launch, or the North Star has crossed its real-read sample floor. Produces POSTMORTEM.md: results scored against the original criteria, one lesson stated as a rule (which must reach past-mistakes.md — a lesson that stays in the postmortem teaches nothing), and an explicit Iterate / Scale / Retire verdict with its evidence. Three-item gate, proved blind in both directions before being trusted: fixtures renamed, no pass/fail tell, grader told both might pass.
Depth reclassification triggers

Auth, payments, 3+ entities, or real users appear → raise the dial to full depth. Kill criterion fires, or 2+ weeks stalled → lower the dial to the lean pass. Both require Gaurav's confirmation and a CLAUDE.md update. Neither changes which phases run.

Purpose

Derive a design language from what the product must prove, rather than applying an aesthetic on top of it. The test: if the design language could be moved to a different product without feeling wrong, it was imposed, not derived.

Operating rule
Never carry design tokens over from a previous projectSeven stages, data before pixels. Tool choices are settled by decision matrices, not preference. The Stage 2 interview is the only source of truth for visual direction, every time.
Stage detail
S0
Data Model
All entities, relationships, and every state — empty, loading, error, populated. Mandatory before any visual work. Output: DATA_MODEL.md.
S1
Brainstorm
Load context, fetch 2–3 live reference UIs, name three design risks (which become the Stage 5 checklist), and define the Named Reader — name, role, context, sophistication, in one sentence.
S2
Interview
One question at a time. Step 0 is a Purpose Statement. Track A derives the design language from that purpose — visual feel, references, fonts, and a negative constraint ("what would make this look AI-generated?"). Track B covers per-panel intent with real copy plus 2–3 auto-suggested animations per panel, confirmed or edited — motion is never an afterthought.
S3
Wireframes
Layout only: component map, key screens, unhappy states, end-to-end flow, and a one-word friction annotation per transition (confusion / hesitation / exit / scroll / load / skip). Excalidraw by default; Figma only if a 3-question matrix says so.
S4
Design System
Every token carries a value plus a usage rule. Component showcase covers default/hover/focus/disabled/error and motion, live-triggerable rather than described. Saved at Documentation/design/design-language.html. Inevitability test runs on the full set. Output: tailwind.config, CSS vars, components.json, brand-guide.md. Claude Design by default; Stitch by matrix.
S5
Spec Doc
What changed this session and why. Required: analytics surface, constraints contract, implementation cost flags (motion complexity flagged here — spring physics, scroll-linked, staggered — with a fallback noted), resolution of all three S1 risks, and a visual changelog with thumbnails.
S6
Handoff
Design ends at spec sign-off. Packet: tailwind.config + CSS vars + components.json + shadcn install list + component showcase + signed SPEC.md. Goes to Blueprint P3.

Purpose

The actual control surface — what's installed, what fires automatically, and what requires a deliberate command.

Operating rule

An action needing Gaurav's explicit approval is a command he types. Automatic checking and bookkeeping, writing a marker, comparing a hash, denying a pattern, runs as a hook with no approval step. A few hooks below are on-demand rather than automatic, noted where that's true.

Session commands
  • /continues Reload project context on demand — also auto-fires at session start via init-project-context.sh, printing Status, Last session, Blocked on, Next up.
  • /end-session Sync memory, journal, decisions, Obsidian. A prior "Coach" phase (naming at most one owned-but-unused capability that would have improved the session) was removed 2026-09-11 as unusable in practice.
  • /compact A built-in that compresses the running context. The manual used to instruct when to call it and what to preserve; that guidance was retired on 2026-08-05 because the harness now compacts on its own and manages what survives.
  • /handoff A third-party skill's own name, reclaimed on 2026-08-09 after a personal command of the same name had shadowed it for months, silently — the plugin skill never even surfaced in the picker. Writes a portable markdown handoff doc to the OS temp directory for four narrow cases (new harness, new directory, a colleague, or forking a side-task mid-session), referencing specs and plans by path rather than copying them.
  • /handoff-compact Rewritten 2026-09-11 into one step. The plugin's own /handoff ships disable-model-invocation: true, which blocks calling it as a skill — it does not block reading its file and following the instructions directly, which is what this command now does each run rather than requiring a manual /handoff first or hardcoding a copy of its doc format that could drift. Then dispatches a fresh (non-fork) agent seeded with the doc. Fresh matters — a fork inherits the full token load, which defeats the point of compacting away from it.

  • commit-message Drafts a Conventional Commits message from the staged diff, matched to the repo's own idiom — never commits or pushes.
  • erd-gate A pass/fail gate on a filled engineering spec before any feature code: an unresolved structural decision or a load-bearing untested assumption blocks the build, and every failure is reported with the exact section quoted. Reads confidence tags in text form ([P]/[S]/[H]/[X]) but deliberately accepts the upstream emoji form too, because a tag a checker refuses to recognise is a tag it silently passes. Proved by a blind test: a reviewer given two unlabelled specs differing in one section returned NOT READY on the unresolved one, naming the failed checks in priority order, and READY on the other.
  • document-skills Authoring and editing for .docx, .xlsx, .pptx, .pdf.
  • session-report Mines local transcripts to show where tokens actually go — by project, skill, and subagent type.
  • skill-creator An eval loop for authoring skills; its description-trigger optimiser targets the usual failure mode.
  • stay-awake A manual, opt-in skill that keeps this laptop from sleeping, hibernating on idle, or sleeping on lid close during a long autonomous run — including on battery — without changing the default power scheme. On this machine idle sleep and idle hibernate were already set to Never on both AC and battery; the one real gap was lid close on battery, which still triggered Sleep. The usual "keep awake" API (SetThreadExecutionState) cannot fix that by itself — Windows explicitly terminates it on a user-initiated sleep such as a lid close, per Microsoft's own documentation. The only real fix is writing the lid-close-action setting to "do nothing" for both AC and battery, and the only way to do that without touching the real default scheme is a disposable duplicate: enable duplicates the active scheme, edits the duplicate only, activates it, and holds the execution-state request as a secondary layer for the display transition; disable reverses all of it and deletes the duplicate. That lid-close setting is also hidden from powercfg by default, so the write briefly unhides it, writes both AC and battery, then re-hides it — confirmed working fully unelevated, no admin prompt. A default 8-hour auto-expiry, a heartbeat file, and a scheduled watchdog task together mean a forgotten enable or a crashed process reverts on its own rather than running indefinitely.
Model routing + autonomous execution
  • The session default is the mid-tier model, set in settings.json. It was the top-tier model on every prompt, including trivial ones, which is where the cost was going. The alias is used rather than a dated model ID, because an alias tracks the current model and a pinned ID goes stale at the next refresh. This was proved rather than assumed. A throwaway headless session was run and asked what it was: it answered with the mid-tier model, which is the only evidence that the key is honoured and not silently ignored. The default and model-escalate-nudge.sh only work as a pair. The default alone would quietly run real work on the wrong model; the hook alone would be pointless, because the default was already the expensive one.
  • model-router Self-triggering skill — fires under the standing "if a skill might apply, invoke it" rule, no hook needed. Tags every plan step inline right before approval: [model: fable] for embedded strategy and planning, [model: opus] for deep analysis and high-stakes judgment, [model: sonnet] for token-heavy routine dev, scripting, testing, and browsing — the default lane. Untagged steps fall back to sonnet with a stated reason, never left blank.
  • dev-manager An opus-model agent that takes an approved tagged plan and executes it autonomously: dispatches each step to its tagged model, defaults to worktree isolation for any parallel dispatch (not conditional on predicted file overlap), and independently re-verifies every worker's claimed result before trusting it. Escalates on exactly six triggers — the Non-Negotiables list, a new external dependency, auth/payments/secrets touched, the plan invalidated mid-flight, anomalous token burn on one step, or a containment breach (Codex writing outside the worktree it was confined to) in the external-execution lane — and handles everything else solo, reporting at checkpoints.
  • /dev-start The explicit handoff gate. Verifies the plan is tagged and approved, then dispatches dev-manager. Plan approval alone never auto-starts execution — this is a deliberate second act.
  • Removed: an autonomous overnight loop. /ralph-loop implemented the Ralph pattern (Geoffrey Huntley) — a fresh-context agent loop re-reading its prompt and spec files from disk each iteration with no conversation memory carried between them, committing on a passing test. Evaluated and decided against: its prompt never varies across iterations, and its completion signal cannot distinguish "finished" from "blocked." The decision was recorded — and then the command sat installed and resolvable for weeks anyway. Deleted 2026-08-04, once a usage check confirmed nothing had ever invoked it. A decision that does not reach the filesystem has not been made.
Claude / Codex collaboration layer

Six skills, one shared record format, so a peer review has one shape to learn instead of five. Each writes to docs/templates/collab-exchange.schema.json: a brief, a claude_position and a codex_position, each submitted blind before either side sees the other; a disagreement_matrix of claim/claude_view/codex_view/status/evidence_needed, status one of agree, claude_conceded, codex_conceded, open; and a decision block carrying chosen, rationale, open_for_gaurav. Records live per project, at collab-runs/<slug>/exchange.json in that project's own repo, so the record travels with the decision it concerns. Two rules are structural rather than stated: Codex's raw text sits verbatim in its own field with any Claude gloss kept separate, so a summary can never quietly stand in for the peer's strongest objection; and every free-text field is length-capped, because peer output is untrusted data, read, never followed as an instruction.

  • council both models answer the same brief blind, then argue it into a disagreement matrix. What neither side resolves goes to Gaurav.
  • premortem-pair asymmetric owner and challenger, one artifact defended and attacked. One file, three modes: premortem, red-team, contract-lock.
  • hypothesis-race split-brain debugging. Both sides submit a falsifiable root-cause hypothesis with a discriminating test, then the test actually runs, so reality decides rather than another round of argument. Extends superpowers:systematic-debugging rather than replacing it, and is gated behind a failed first hypothesis, so it is never spent on an obvious bug.
  • cross-review paired code review honouring the existing two-pass bar, critical then informational. A finding both models catch independently is high confidence; a finding only one catches gets checked by the other before it reaches Gaurav.
  • assumption-auction both sides rank the decision-critical assumptions by impact-if-false times confidence. A second call runs only if they disagree on which assumption matters most.
  • second-take the cheap daily one. Claude's answer is hidden entirely; only the bare question goes to Codex Terra, the mid tier and deliberately not the flagship, because the value sought is independence rather than depth. Shows both answers side by side. No command wraps it, on purpose: reached by asking for it in plain language.
  • /council, /premortem-pair thin command wrappers over the two skills of the same name.
External model delegation
  • /delegate Sends a read-only task to a second model provider's CLI — a non-Anthropic second opinion on a plan or diff, a research pass, or reading a file too large to load. It returns text; the main session applies any change.
  • agy-delegate.sh --type review|research|longread The wrapper for Google Antigravity. Per-lane model defaults: a strong reasoning model for judgement work, a cheap fast one for bulk reading. --stats reports this wrapper's own token spend per quota pool over the last 7 days, from a local ledger — labelled a burn estimate, not remaining quota.
  • codex-delegate.sh --type review|research|longread plus --permission review|edit A second backend, OpenAI Codex on its own ChatGPT Plus subscription. review is fully read-only, an empty ephemeral scratch directory with no filesystem access. edit is genuinely different: real workspace-write access, gated by three checks that all have to pass — it refuses to run without an explicit --dir, refuses if that directory is not inside a git repository, and refuses if that directory resolves to the repo's main working tree, checked by resolving --dir to its actual repo root first rather than comparing the typed path as a string (a subdirectory of the main tree is never string-equal to the main tree's root, and the first version of this check missed exactly that). --resume ID continues a previous Codex session so a multi-round exchange does not have to start over each round — edit-path only, since a review-path run is ephemeral and never written to disk.
  • Four Codex models, picked per call and never defaulted: gpt-5.6-sol flagship and deepest of the 5.6 line, gpt-5.6-terra mid, gpt-5.6-luna fast and cheap, and gpt-6-astra — the newest generation (GPT-6), most capable, most expensive against a limited Plus allowance, verified live 2026-09-09 and deliberately opt-in only, never suggested or defaulted, so Gaurav is always the one who chooses it. The Sol/Terra/Luna tier order was corrected 2026-08-27: four files had it backwards for as long as the lane existed, caught by Gaurav and then checked against the vendor's own published docs before a single file was touched, because a correction taken on trust is just a second guess.

The Agent tool's model parameter is a closed enum of first-party models, so no subagent can be spawned onto another provider's model — a second provider is reachable only by shelling out, which is why this is a tool and not an agent. Run headless, a tool call cannot prompt for permission, so it auto-denies and can return an empty response wearing a success mask; the wrapper scripts assemble every payload themselves rather than letting the CLI read anything on its own, so read-only stays structural, large content never enters the main session's context, and no turns are burned on denied calls. model-router can now tag a plan step for the Codex execution lane, added 2026-09, which runs the whole git surface (prepare a worktree, stage once, scope-check, commit, verify, assert nothing else moved) through one script the executor never bypasses with its own git command — reviewed at the plan-branch boundary before it reaches the trunk, per-run consent recorded on disk, every commit authored under a fixed name so what the external model wrote is one command to list.

Guardrail hooks and scans (most fire automatically; a couple are on-demand, noted inline)
  • pre-tool-use-guard.sh Blocks git push --force, --no-verify, home-directory rm -rf, reset-and-push chains, echoing secret-shaped vars to output, python3 where only python exists, and quoted Windows paths with the trailing-backslash bug that breaks bash parsing. Also covers PowerShell shapes (Remove-Item -Recurse -Force, $env: secret variables, git flags smuggled through powershell -c/cmd /c). File layout (split 2026-08-06, fourth file 2026-08-07)

The manual is no longer one file. ~/.claude/CLAUDE.md holds how Claude works: the gears, the priority order, the tripwires, output style, and the quality thresholds. What Gaurav owns, and what expires, lives in four files under ~/.claude/context/: estate.md (hosts, domain, VM, analytics), knowledge.md (memory locations, Obsidian, Notion, capture routing), tooling.md (framework contract, skill precedence, delegation, the enforcement register) and model-notes.md (tuning for the current model generation). They are pulled back in with bare @path import lines.

The fourth file was split out on 2026-08-07. The model-specific rules had been living inside the manual behind a note saying the section expires at every model launch, which is a reminder rather than a mechanism. Moving them out makes a model launch a one-file swap, and the file is replaced wholesale rather than appended to. The idea came from someone else's setup and the delivery did not. Their version appends the rules to the system prompt from a shell wrapper, which means the rules only apply to sessions started through that wrapper: not the desktop app, not the IDE extension, not scheduled agents, not subagents. An import loads on every path. It is also visible to the checks, and a rules file the checkers cannot see is the same split-copy problem this setup has already been bitten by twice.

The split axis is "how Claude works" versus "what Gaurav owns", not topic and not change frequency. Frequency is the symptom: the manual changes a few times a year, the estate changes whenever a service is added or retired. Putting them in one file meant every new service edited the operating manual, and a manual that reads like an inventory stops being read. The axis also settles where a new subsystem's facts go on day one, which a topic split does not. model-notes.md is the one deliberate exception, and it is worth naming rather than hiding: it holds neither how Claude works nor what Gaurav owns, but what stops being true at the next model launch. It earns its own file because it is the only content with an expiry date, and content that expires needs somewhere to be replaced wholesale without touching anything that does not.

Imports, not links, and the two are not interchangeable. A bare @path line is read into context automatically at load, recursively, to 5 hops. A markdown link or a bare path is never read unless the model chooses to open it. The requirement was that routed content is always present, so only an import satisfies it. This buys zero tokens. Cost is unchanged, and the win is purely that the small files are edited often while the manual stays put. That trade was made explicitly. Each import is paired with a one-line trigger naming the moment its content is load-bearing: the import handles presence, the trigger handles attention.

Proven before it was built. Nothing in the setup had ever used an import, so the whole design rested on an untested assumption. A probe file with a unique token was imported and returned in a fresh session; with the import line removed and the file still on disk it returned nothing, which is the control that actually proves the import is doing the work; and the same path inside backticks also returned nothing. A broken import is silent at load time. No error, the content simply is not there. That is why all four paths are tracked in the mirror manifest and why the installer seeds them per-file.

Two caps, both self-declared in the file's own header and read from it rather than hardcoded. The manual has its own byte cap. The gate, though, is the total across the manual and everything it imports, because splitting with imports moves bytes out of the file without moving them out of the load. The per-file cap went green at 5.5 KB while the real cost stayed near 11 KB. A cap that reports green on a world that no longer exists is a check that always passes, which is treated here as identical to a check that always fails.

Purpose

The problem was never security posture. It was that keys got copied by hand with no single place to put one, so time went into hunting for a key already owned — and sometimes a new one got issued instead. So the tools were judged on capture and search first, sync second, and that reordering eliminated the option that had been leading.

Method

gopass (the Go rewrite of the classic Unix pass), a local GPG-encrypted store, versioned as a git repository, with a bare remote on a synced cloud drive as the off-machine copy. Every secret is encrypted to two recipients — a daily key on the laptop and a backup key whose private half does not live on it — because one key is one disk failure away from losing everything. Free, local-first, and no vendor holding the plaintext.

Four gates, in order, none skippable
  • Two recipients before the first real secret. One recipient would encrypt everything to a single key and report nothing.
  • A canary secret and a search wrapper. The tool prints "no matches, no errors" when every decryption has failed, and exits 0 either way. A false not-found is precisely what causes a duplicate key to be issued.
  • One crypto binary across both shells. Two were installed with separate keyrings, so a store readable in one shell and not the other is the same silent class as the gate above.
  • A remote, plus a restore proved with the backup key alone. Until that runs, two-recipient encryption is a claim.
starters/gopass/gopass-search.sh (and a .ps1 twin for the other shell) — why it exists at all
A dependency can lie in both directionsThe store's own search reported zero errors while every decryption failed, and separately reported zero matches in the same output as a line naming a match. So the wrapper ignores the tool's summary entirely and reads the per-item lines. Nothing believes a "no results" until a known sentinel finds itself first.
What does not go in
Dead credentials are skipped, not filedA revoked key in the store answers "you already have one" about something that authenticates nothing — the store's own purpose inverted. The test for whether skipping is safe is whether losing it could cost anything. A retired service is not a revoked credential, and that distinction saved a token that would otherwise have been reissued.
Decision history

A secret manager was chosen, and reversed two days later. Nothing had to be undone because nothing had been built yet. The original decision had itself written the rule "capture and search first, sync second," and then picked a tool that loses on it — applying that entry's own rule was enough to reverse it. Its homepage had also claimed platform parity that its own FAQ didn't confirm and a third party denied, so the eventual choice was proved rather than believed: an official installer, both shells passing, and an accidental overwrite recovered by decrypting the pre-overwrite value back out of git history — the exact scenario the rejected tool's free tier calls unrecoverable.

The restore proof passed and the backup was still broken

A real secret was decrypted from a clone of the remote using only the backup key, hash-identical to the primary-key decrypt, with an empty keyring as a control that correctly failed. Every secret was recoverable and the gate would have been signed off on that. Then the clone was diffed against the live copy and the recipient list came back with the wrong line endings — the crypto tool rejects a fingerprint with a stray carriage return. So the ciphertext restored perfectly while the restored store could not have encrypted the next secret, and the tool ignores an unusable recipient quietly. It surfaced only because the plan said to verify the remote by cloning it back and diffing, rather than reading push output — a push that reports success says nothing about whether a checkout of it works. Fourth instance of this line-ending class in this setup; every previous fix was scoped to the files in front of it, so the standing question is whether the global setting should change rather than be patched a fifth time.

A documented path was corrupted by the tool that wrote it

The setup sheet carried a raw control character inside a path, sitting in the block explicitly labelled do not re-derive. Not a typo: a stream editor's replacement text interprets backslash escapes, so writing a Windows path through a substitution turns the folder separator plus certain letters into control characters, silently. Three attempts to fix it failed in three different ways that all looked identical from outside. What generalises: read the value back as bytes, or you are checking the renderer and not the file.

starters/gopass/gopass-migrate-env.sh — two rules it is built on
  • It never prints a value. Not on success, not in an error, not in a preview. Errors name the key and the line number. A migrator that echoes a credential into a terminal scrollback has defeated the store it fills.
  • It refuses rather than guesses. The whole file is parsed and every conflict checked before the first write, so a bad line late in a file cannot leave the earlier ones migrated. A partially migrated project is worse than an untouched one, because it looks done. An ambiguous value that a conventional parser would silently truncate is refused instead. An empty result is a refusal, not a success. A skip instruction naming something not present is refused too.

Its suite was falsified with two deliberately broken stand-ins before being trusted — one that always succeeds and one that always refuses, producing 27 and 36 failures respectively against zero for the real thing. Every refusal case additionally asserts that nothing was written, not merely that the exit code was right.

A measurement that changes how it gets used
Name search is instant; content search is notSearching secret names returns in about a tenth of a second. Searching decrypted contents takes almost forty, because it decrypts everything, and that cost grows linearly with the store. The question the store exists to answer — "did I already make one of these?" — is a name question. Worth knowing before the store doubles.

Why this page exists

This is disaster-recovery material. If the setup has to be rebuilt on another machine or another account, the git repo plus this page is what makes that possible — which is why the sync is a standing rule rather than a nice-to-have, and why no credential ever appears here.

The setup is versioned, because a setup is a system and systems drift. A version is a point-in-time inventory of both halves — this framework repo and the global ~/.claude/ config — so any past state can be described, compared, and restored. Setup and Playbook answer what and when. This tab answers how it got here, including where it is currently inconsistent.

Why version a config at allSession journals record changes and git log records one repo. Neither answers "what did my whole setup look like on this date" — and only one of the two halves is under git. A version is cut when the shape changes (a framework, hook, skill, agent, command, plugin, or vendored release), not on every edit.
What changed

Both operating manuals were rewritten from scratch, and the audit that justified the rewrite was compiled into a script so it does not have to be repeated by hand at the next model launch. The trigger was the Claude 5 generation: Anthropic’s own prompting guides now say to remove verification instructions, anti-laziness pressure and hedging language, all three of which this setup carried, and Anthropic deleted more than 80 percent of Claude Code’s own system prompt for the same reason. The files had not changed. The models had.

The rule that defines this version
A section that expiresBoth manuals now carry a dated block holding everything written to compensate for a model weakness, stamped with the model and CLI version it was written against. Everything else in the file is durable fact. At the next model launch only that section is reviewed. The previous shape had no such boundary, so a migration meant re-reading and re-arguing the whole file, which is a review that does not happen.
What was removed, and why each

Instructions to verify more and to re-check finished work, because these models self-verify and the guidance states that removing such instructions reduces wasted tokens with no loss in quality. Standing anti-agreeableness pressure, because these models are direct by default and the instruction turned pushback into a ritual. A design vocabulary lookup table, because current models read design feedback natively. Manual compaction guidance, because the harness compacts on its own. And the prose copies of every rule a guard already enforces, which the manual’s own first lines had said belonged in hooks.

Two contradictions closed

The two manuals were 85 percent identical and had drifted into disagreeing with each other while both loaded at once: one claimed a phase count that was one short of the phases that exist, and pointed memory at a folder the other forbade. The project manual is no longer a copy of the global one, so that class of drift cannot recur the same way.

The new check, and the run that corrected it
A linter that fires on every use of a word is the same as one that fires on noneThe new evaluator lints any manual against the current model generation, with every rule citing the documented behaviour change it defends against. Its first real run across the fleet reported two stale findings and both were wrong: one was product prose about a dashboard being untrustworthy, the other a domain rule about checking codebase conventions. A published audit of 74 real manuals found the same thing, that none of its 45 mentions of verification were the kind the guidance targets. The rules were narrowed to match only instructions aimed at the model’s own output, the four false positives became test cases, and findings across the fleet fell from 37 to 3. Acting on the first run would have deleted load-bearing lines from two projects.
