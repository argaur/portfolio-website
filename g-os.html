File layout (split 2026-08-06, fourth file 2026-08-07)

The manual is no longer one file. ~/.claude/CLAUDE.md holds how Claude works: the gears, the priority order, the tripwires, output style, and the quality thresholds. What Gaurav owns, and what expires, lives in four files under ~/.claude/context/: estate.md (hosts, domain, VM, analytics), knowledge.md (memory locations, Obsidian, Notion, capture routing), tooling.md (framework contract, skill precedence, delegation, the enforcement register) and model-notes.md (tuning for the current model generation). They are pulled back in with bare @path import lines.

The fourth file was split out on 2026-08-07. The model-specific rules had been living inside the manual behind a note saying the section expires at every model launch, which is a reminder rather than a mechanism. Moving them out makes a model launch a one-file swap, and the file is replaced wholesale rather than appended to. The idea came from someone else's setup and the delivery did not. Their version appends the rules to the system prompt from a shell wrapper, which means the rules only apply to sessions started through that wrapper: not the desktop app, not the IDE extension, not scheduled agents, not subagents. An import loads on every path. It is also visible to the checks, and a rules file the checkers cannot see is the same split-copy problem this setup has already been bitten by twice.

The split axis is "how Claude works" versus "what Gaurav owns", not topic and not change frequency. Frequency is the symptom: the manual changes a few times a year, the estate changes whenever a service is added or retired. Putting them in one file meant every new service edited the operating manual, and a manual that reads like an inventory stops being read. The axis also settles where a new subsystem's facts go on day one, which a topic split does not. model-notes.md is the one deliberate exception, and it is worth naming rather than hiding: it holds neither how Claude works nor what Gaurav owns, but what stops being true at the next model launch. It earns its own file because it is the only content with an expiry date, and content that expires needs somewhere to be replaced wholesale without touching anything that does not.

Imports, not links, and the two are not interchangeable. A bare @path line is read into context automatically at load, recursively, to 5 hops. A markdown link or a bare path is never read unless the model chooses to open it. The requirement was that routed content is always present, so only an import satisfies it. This buys zero tokens. Cost is unchanged, and the win is purely that the small files are edited often while the manual stays put. That trade was made explicitly. Each import is paired with a one-line trigger naming the moment its content is load-bearing: the import handles presence, the trigger handles attention.

Proven before it was built. Nothing in the setup had ever used an import, so the whole design rested on an untested assumption. A probe file with a unique token was imported and returned in a fresh session; with the import line removed and the file still on disk it returned nothing, which is the control that actually proves the import is doing the work; and the same path inside backticks also returned nothing. A broken import is silent at load time. No error, the content simply is not there. That is why the three paths are tracked in the mirror manifest and why the installer seeds them per-file.

Two caps, both self-declared in the file's own header and read from it rather than hardcoded. The manual has its own byte cap. The gate, though, is the total across the manual and everything it imports, because splitting with imports moves bytes out of the file without moving them out of the load. The per-file cap went green at 5.5 KB while the real cost stayed near 11 KB. A cap that reports green on a world that no longer exists is a check that always passes, which is treated here as identical to a check that always fails.

Purpose

The problem was never security posture. It was that keys got copied by hand with no single place to put one, so time went into hunting for a key already owned — and sometimes a new one got issued instead. So the tools were judged on capture and search first, sync second, and that reordering eliminated the option that had been leading.

Method

A local GPG-encrypted store, versioned as a git repository, with a bare remote on a synced cloud drive as the off-machine copy. Every secret is encrypted to two recipients — a daily key on the laptop and a backup key whose private half does not live on it — because one key is one disk failure away from losing everything. Free, local-first, and no vendor holding the plaintext.

Four gates, in order, none skippable
  • Two recipients before the first real secret. One recipient would encrypt everything to a single key and report nothing.
  • A canary secret and a search wrapper. The tool prints "no matches, no errors" when every decryption has failed, and exits 0 either way. A false not-found is precisely what causes a duplicate key to be issued.
  • One crypto binary across both shells. Two were installed with separate keyrings, so a store readable in one shell and not the other is the same silent class as the gate above.
  • A remote, plus a restore proved with the backup key alone. Until that runs, two-recipient encryption is a claim.
Why the search wrapper exists at all
A dependency can lie in both directionsThe store's own search reported zero errors while every decryption failed, and separately reported zero matches in the same output as a line naming a match. So the wrapper ignores the tool's summary entirely and reads the per-item lines. Nothing believes a "no results" until a known sentinel finds itself first.
What does not go in
Dead credentials are skipped, not filedA revoked key in the store answers "you already have one" about something that authenticates nothing — the store's own purpose inverted. The test for whether skipping is safe is whether losing it could cost anything. A retired service is not a revoked credential, and that distinction saved a token that would otherwise have been reissued.

Why this page exists

This is disaster-recovery material. If the setup has to be rebuilt on another machine or another account, the git repo plus this page is what makes that possible — which is why the sync is a standing rule rather than a nice-to-have, and why no credential ever appears here.

The setup is versioned, because a setup is a system and systems drift. A version is a point-in-time inventory of both halves — this framework repo and the global ~/.claude/ config — so any past state can be described, compared, and restored. Setup and Playbook answer what and when. This tab answers how it got here, including where it is currently inconsistent.

A version is cut when the shape changes (a framework, hook, skill, agent, command, plugin, or vendored release), not on every edit.

Personal utility skills
  • stay-awake A manual, opt-in skill that keeps this laptop from sleeping, hibernating on idle, or sleeping on lid close during a long autonomous run — including on battery — without changing the default power scheme. On this machine idle sleep and idle hibernate were already set to Never on both AC and battery; the one real gap was lid close on battery, which still triggered Sleep. The usual "keep awake" API (SetThreadExecutionState) cannot fix that by itself — Windows explicitly terminates it on a user-initiated sleep such as a lid close, per Microsoft's own documentation. The only real fix is writing the lid-close-action setting to "do nothing" for both AC and battery, and the only way to do that without touching the real default scheme is a disposable duplicate: enable duplicates the active scheme, edits the duplicate only, activates it, and holds the execution-state request as a secondary layer for the display transition; disable reverses all of it and deletes the duplicate. That lid-close setting is also hidden from powercfg by default, so the write briefly unhides it, writes both AC and battery, then re-hides it — confirmed working fully unelevated, no admin prompt. A default 8-hour auto-expiry, a heartbeat file, and a scheduled watchdog task together mean a forgotten enable or a crashed process reverts on its own rather than running indefinitely. Building it surfaced several real bugs only live testing against actual Windows power state caught: the lid-close setting sits under a different settings subgroup than assumed, two flag-casting bugs silently killed the background process holding the execution-state request, and a timestamp round-trip through JSON was corrupting day and month until timestamps were stored as plain numbers instead of date strings. One edge case came from an interrupted test run on this exact machine: a hard-killed process can leave the temporary scheme active with no state file to say what the real original was, so enable now recognises that specific orphaned state by name and recovers to a known-safe default rather than trusting it.

Guardrail hooks
  • pre-tool-use-guard.sh Blocks git push --force, --no-verify, home-directory rm -rf, reset-and-push chains, echoing secret-shaped vars to output, python3 where only python exists, and quoted Windows paths with the trailing-backslash bug that breaks bash parsing. Rewritten pure bash after the same fail-open class was found here too — the third instance. It parsed the payload through an interpreter and emitted its deny from an interpreter heredoc; on this machine that interpreter resolves only to an unrelated third-party virtualenv, so the gate would have silently allowed every forbidden pattern the moment that venv moved. Proven, not argued: under a PATH with the interpreter removed, the old hook returned empty output and exit 0 — allow — for a force-push; the rewrite denies. Three further changes came out of it. It now fails closed: a payload carrying a command it cannot parse is denied, where the old code treated an unreadable command as nothing to check. Its extraction no longer uses the greedy pattern the deploy guard carried until it was fixed too, so sibling fields in the payload cannot leak into the command being judged. And it covers PowerShell shapes — Remove-Item -Recurse -Force on home or a drive root, $env: secret variables, and git flags smuggled through powershell -c or cmd /c wrappers, which no bash-syntax regex had ever matched. The secret check was also tightened to require a real variable reference rather than a bare English word, after it blocked a legitimate echo of a section heading — a gate that cries wolf gets routed around, which is its own kind of failure. Then the same failure mode appeared twice more, and it is the important one: the guard could not tell a forbidden pattern being executed from one being mentioned. It denied a git commit whose message described a force-push, and denied a jq filter that merely named a permission entry, because the ( inside a quoted string read as a command position. In a setup whose whole purpose is documenting its own guardrails, that is not an edge case. Commit message bodies are now scrubbed before the checks run — non-greedy, so a command chained after the message stays in the checked string, and an early-closed quote fails closed. Also added: printenv, PowerShell Env: read paths, and the console.log/puts/System.out.println family of output verbs; cmd-shape recursive deletes (rd /s /q); and backtick-escaped Windows paths. One extension was refused: matching secrets across a pipe, because every formulation of it also denied a routine authenticated curl … | tee, which never prints the value. The motivating leak was solved by widening the verb vocabulary instead of the structural scope — prefer that trade every time. Finally, a speed pass with a lesson in it. Every check ran as a separate printf piped into grep — around ten subprocess pairs on every single command, costing about 1.5 seconds per call. Converting them to the shell's own built-in pattern matching took it to 366 ms, and the deploy guard from 562 ms to 272 ms: roughly 1.5 seconds returned to every command the agent runs. Rewriting ten regexes inside a security gate is only safe because the suite below can falsify it, and it was re-falsified in both directions afterwards rather than merely re-run. One thing this guard still gets wrong: it cannot be used to document itself. Writing prose about the delete patterns it catches trips it, because the carve-out for quoted text was scoped to commit-message bodies rather than to quoted data positions generally. A gate that blocks its own documentation gets routed around, which is the failure the carve-out existed to prevent. That defect is still open, and it fired again while this page was being written: appending a decision entry that quoted a permission string was denied, because the carve-out covers commit message bodies and not heredocs. One check was added later, and the gap it closed says something about how these checks get scoped. All four of the guard's secret checks required a secret-shaped variable. Not one of them looked at a secret-shaped file. So reading a credentials store or an environment file passed cleanly, verified by running it: the live guard returned empty output and exit 0 for all four forms tried. The rule in the manual said not to read those files. Four checks sat next to it, none of them enforcing it, because each had been written to close a specific leak rather than to cover the class. The new check reads its path list from a single shared file, which the write-and-read gate below also sources, because the same rule now has to hold on two different tool surfaces and two copies of a list drift silently while both sides keep passing their own tests.
  • deploy-preflight-guard.sh Blocks vercel --prod and railway up unless the target project's CLAUDE.md records a Deploy target: line — preventing a deploy to the wrong account by construction. Rewritten after being found broken in both directions: it had been resolving CLAUDE.md against the hook's own working directory rather than the project being deployed (so it blocked every deploy), it never JSON-unescaped the command (so a quoted cd path parsed as garbage), and it parsed via an interpreter with 2>/dev/null — meaning a missing interpreter made it exit 0 and allow the deploy. Now pure bash with no interpreter dependency, and a 13-case suite asserting allow and deny. The general rule it produced: a gate must fail closed when its own dependencies are absent, and needs a functional test, because a guard that never fires and a guard that always fires look identical from outside. Those 13 cases lived only in session memory until they were persisted into the harness below, and persisting them exposed a fourth defect — the command was extracted with a greedy pattern that captured through to the last quote on the line, so the payload's description became part of the command. A description containing the words "cd into…" made the guard resolve the wrong directory and block a correctly-documented project. Same failure as its original bug #1, reached by a different route, and a reminder that fixing a hook is not the same as fixing the parsing it shares with every other hook. Now fixed: it uses the character-walk extraction that stops at the first genuinely unescaped quote, and it fails closed — a payload carrying a command it cannot read is denied, because the guard cannot tell whether that command is a deploy. The extraction was duplicated into it rather than shared from a common library, deliberately. Sharing would be tidier, but every failure in this setup's history has been a dependency that went missing; a gate with no external dependency cannot be disabled by one.
  • hook-canary.sh A SessionStart hook that answers, every session and without being asked, whether the guardrails are actually working. For each registered hook it checks the file exists, parses, and has a resolvable interpreter; for each gate it pipes a known-deny fixture and requires a deny, then a known-allow fixture and requires silence. It is silent when green — zero output — and shouts only on failure, which is the only way a startup check survives more than a fortnight. It exists because the failure it catches is invisible to every other habit in this setup: a guard can be present, registered, syntactically valid, committed, and documented, and still be the wrong version. Pointed at a fail-open stub it reports the gate as unblocked, including when the stub carries the correct filename in a different directory. Later extended to answer a second question the smoke tests could not: does the live setup still match the repo? The trigger was finding that the install script had become the regression. It copied a 44-line guard from the repo over the tested 440-line live one, reverting a fail-open fix, because the repo copy had been left behind while the live file was rewritten. Worse, 8 of 13 registered hooks had no repo copy at all, so a machine rebuilt from git would have come up with most of its enforcement layer simply absent. Two sync paths existed and neither closed the loop: one pushed repo to live, the other pulled live into a separate audit folder nobody installed from. The canary now asserts that every registered hook matches its repo copy, and separately that every command in the repo is installed and matches. Both run in two subprocesses total, one checksum pass per side, so the cost does not grow with the number of files. The command check runs in one direction only, repo to live, because roughly 29 installed commands come from third-party marketplaces the repo does not own; checking the other way would warn on every session, and a check that always warns is one nobody reads. For the same reason a drifted command is a warning while a drifted hook is a failure: keeping "failure" to mean a guard stopped guarding is what makes it worth reacting to. The most convincing result during development was that it caught itself, the moment its own live file was edited without the repo copy being updated. Extended again to cover skills and agents, and the gap it closed is the clearest argument for the whole approach. Two skills sat in the repo, never installed, while a command referenced one of them by name. So a session reaching that phase called a skill that was not on disk. The cause was not a missed sync: the install script had never installed skills at all, in any version. The check that would have caught it covered hooks and commands and stopped there, and that narrowness is itself what the audit later identified as the source of the next three drifts. One design point is worth keeping. Hooks and commands are flat sets of files, so a filename alone identifies each one. Skills are folders, and every skill contains a file with the same name, so identifying them by filename collapses them all into one and reports the wrong one. They are compared by their path within the skills folder instead. A comparator that covers four surfaces is worth more than four rules saying to keep them in step.

So the backup had silently been running only when a human remembered to invoke it manually. The marker is the point: a hook that exits 0 having done nothing is indistinguishable from one that worked, unless it is made to leave evidence.   • memory-index-check.sh A SessionStart hook that answers whether every session journal is actually reachable. A journal is only readable if the index file lists it, and an unlisted one is invisible no matter how well it was written. The rule already existed in prose, in the wrap-up command, under a heading reading "REQUIRED, never skip", added after an earlier incident that lost seven sessions. It is prose, so nothing ran it, and a later count found 44 journals across 9 projects unreachable. That mismatch is the whole lesson: the setup's own manual says deterministic requirements belong in a hook, not in a file of judgement, and comparing two lists is about as deterministic as work gets. Writing the instruction more forcefully was the one fix already proven not to work. Two design choices carry the weight. It compares sets, not counts, because equal counts hide the case where one journal is missing from the index and one index entry points at a deleted file; a count check reads that as healthy while both sides are wrong. And it reads both memory locations, because most projects keep memory outside their repo, so a check reading one place is blind to the majority of them, including every one of the worst cases. It also reports a project whose memory has split into two folders that disagree, which is worse than missing memory, because a later session reads one half and trusts it. Silent when clean, 23 test cases, and an audit mode that sweeps every project at once. The first thing that mode did was find a bug in the sync script written minutes earlier, in a folder the hook itself would never have been pointed at. All 44 journals were later repaired, each index line written from the journal's contents rather than its filename, because a line generated from the filename satisfies the check and leaves the material just as unfindable. One project turned out to hold two memory folders whose contents genuinely disagreed: the same two files existed on both sides with different material in each, so keeping either side whole would have destroyed the other. They were merged rather than chosen between. A caution about the clean result that followed. The sweep mode returns before it reaches the split-folder logic, and it only recognises files whose names follow the journal convention. So a clean sweep proves journals are indexed. It does not prove one folder per project, and reading the narrow green as the broad one is how a genuinely split project stayed hidden through a run that reported no problems. Both limits are now fixed, and the shape of them is worth keeping. The sweep mode is the one a person runs deliberately when they suspect split memory, and it was the one mode that could not detect it. The logic existed; it sat in the other branch. Nothing was missing except a call. The name recognition was the same kind of narrowness: memory files that are not journals were invisible, so a folder holding only project notes and page snapshots read as empty, and an empty folder with no index is skipped as a project that has not started writing memory yet. The project this hid held real material on one side only. It was merged the same session the check learned to see it, which is the right order: fix the instrument, then let the fixed instrument certify the repair. A check whose blind spot is exactly the case it was built for is worse than no check, because it converts an open question into a false answer.
  • file-io-guard.sh A PreToolUse gate on the write, edit and read tools. It is listed last because it is newest, and because what it replaced was nothing at all. The setup accumulates a memory corpus across every project, and that corpus is the thing the whole arrangement exists to build. It was defended by one sentence in a manual: edit memory surgically, never rewrite a whole file. Checking what actually enforced that sentence turned up a chain of backstops that all failed in order. No gate ran on the write tool, at any point. No deny list existed in any of the four settings files. The local backup repository had no automatic commit and no remote. And the vault sync copies with overwrite, so a corrupted file propagates to the backup at the end of the same session that corrupted it. One write could replace a ninety-thousand byte decision log, silently and permanently. The gate now denies a write to a memory file whose new content is a fraction of what is already on disk, with an escape hatch named in the refusal message, because a rewrite is sometimes genuinely intended and a gate with no legitimate exit is one people disable. It also denies reading a credentials store, an environment file, or a key, which is the same rule the command guard now enforces on the shell side, read from the same shared list. The threshold is the part worth being honest about. Set too tight, it fires on ordinary edits, earns a reputation for false alarms, and gets routed around, which is exactly how a different gate in this setup failed. It was tuned against the real file sizes it protects rather than a round number, and proved in both directions: truncating the real decision log is refused by name, while an ordinary edit and a rewrite with the escape hatch set both pass in silence. Alongside it the backup repository gained an automatic commit at session end, and deliberately no remote. The audit that produced this work recommended both. Only one was taken. The tracked configuration includes a file carrying a live server address and key path, so pushing the tree would have closed a backup gap by opening a disclosure gap. A local commit history is enough to make a bad write recoverable, which is the loss this was about.
  • smart-zone-nudge.sh A UserPromptSubmit hook built after watching a third-party skill author's video on session handoff, once the transferable idea turned out to be narrower than the pitch. Nothing in this setup watched session size before it. Claude Code exposes no live token count to a hook, so it estimates from what does exist: the transcript file's byte size, divided by four, against a threshold the source video's own documentation calls "the window within which the model still reasons sharply" rather than a hard limit — which is why the estimate is stated as an estimate and not dressed up as precision it doesn't have. A hook can only nudge, never act. It cannot invoke a skill or spawn an agent itself, so "automatic" here means it injects context telling the assistant to offer /handoff-compact and wait for a yes — never a silent context switch out from under the person mid-session. It dedupes per session rather than per prompt, on a marker file holding the last-notified token count, so crossing the line once produces one nudge, not one on every following prompt — and re-fires only past a further third of the threshold in growth, so a session sitting flat past the line goes quiet rather than nagging every turn.
  • /handoff-compact composes rather than duplicates.   • model-escalate-nudge.sh A UserPromptSubmit hook that exists because the session default moved to the cheaper model. A non-zero exit on this hook event can discard the prompt the user just typed, which would turn an advisory check into data loss, so every path exits clean and a trap enforces it. The saving is the subagent, not the default. An escalated agent reads what it needs, works, and returns only its report, so the expensive model is paid for the hard part and the cheap one for every conversational turn around it. Gate testing
  • scripts/check-all.sh One command that runs every check, and the reason it exists is a suite nobody had named. The payload suite below is the slowest and most visible one, and it covers the pre-tool guards and nothing else. Ten other suites and five standalone checks had no command that ran them, so running them was a rule enforced by a person remembering. Two of them sat red for a full day while every session reported green. The obvious fix is a runner with a list of suites in it, and that reproduces the same failure one level up — the eleventh suite had been invisible for months purely because its filename did not match the pattern every document used to describe it. So the runner discovers suites instead. That moves the risk rather than removing it: a glob matching fewer files than it should reports green over a smaller set, which is the same shape as a truncated manifest verifying clean. So two floors refuse rather than warn — the discovery count must meet a declared floor, and every deliberate exclusion must still name a file that exists, because a rotted exclusion and an intentional skip are indistinguishable from the outside. One check is wired as a ratchet rather than pass/fail: it reports a standing backlog owned by other projects, so making it a gate would leave the runner permanently red, and a permanently red gate is one people stop reading. Its count may fall and never rise. The test suite for the runner hides a real suite and asserts the runner refuses, because that case is the original bug.
  • scripts/hook-tests/run.sh The answer to "how do you know a guardrail works." 234 functional cases, pure bash plus jq, each piping a realistically-shaped payload into a real hook on stdin and asserting its actual output and exit code. Existence checks do not count — "is the hook present and registered?" passes a hook that is broken in code and a hook whose output nobody reads, which is exactly how two separate defects survived an audit. Every gate ships at least one allow case and one deny case, because proving a guard fires is only half of it; proving it stays quiet on legitimate work is what stops it being disabled. Three properties earn their keep: the runner aborts if any declared case went unscored, so a suite can never report green having tested nothing; the hook path is overridable, so a candidate rewrite is tested standalone before it is swapped into a live session; and a case can run under a modified PATH, which is how the interpreter-dependency fail-open is proven closed rather than assumed. Falsified deliberately in both directions — pointed at an always-allow stub, every deny case fails; pointed at an always-deny stub, every allow case fails. A suite that cannot fail proves nothing.
  • A third-party tool can write into the file your guardrails live in, and yours is the only thing that would notice. A terminal tool installed itself mid-session and added roughly eleven hook registrations plus a status-line override to the global settings file. The behaviour was benign: each one posts to a token-guarded loopback port, and only when that tool’s own environment variables are set. Three things made it worth reverting anyway. It edits the file the enforcement layer lives in, without asking. Every registration spawns a shell on events that fire constantly, taxing sessions the tool never launched, against a start-up budget that had been measured to a tenth of a second. And every command was base64-encoded, so nothing in the setup reads it as text and no amount of care while reading that file would have surfaced it. The live-versus-committed comparator caught it inside an hour. That comparator had been treated as hygiene — a tidy-up that keeps a mirror honest. It is the only mechanism here that watches for changes nobody in the session made. The revert used the pre-change snapshot rather than hand-filtering the encoded blobs, after confirming every difference was an addition and nothing of the owner’s had been removed. The tool stays installed, and the decision entry says plainly to expect the hooks back on its next launch, so the next red is a ten-second diagnosis instead of an investigation.
  • Consolidating a rule into one file is not the same as validating it. The set of "files that hold a secret" was moved into a single definition that both guards source, so the two could never disagree. That fixed drift between the enforcers and said nothing about whether the definition matched reality. It did not: the pattern matched a name led by a dot, so a file named the other way round — a word, then the extension — sailed through, and that was the precise filename of a credential this setup had already found leaked in a public repo months earlier. Password-manager config, database password files and keystores were missing too, and so was every key using the algorithm that has been the default for years, because the pattern was written for the older name. The obvious fix was still wrong. Matching the conventional prefix looked complete and would have missed one of the two real private keys present, since the key-generation tool names a key after its algorithm and does not require that prefix. Deduplication removes disagreement between copies; it never tests the surviving copy against the world. When a rule is consolidated, enumerate the real instances on disk and run them through it — here that was two find commands, and both produced a name the function allowed. Write the deliberate exclusions into the file with their reasoning, so the next reader can tell "nobody thought of it" from "covering it breaks legitimate reads". One exclusion is deliberate here for exactly that reason: the pattern that would catch the last stray name also denies two ordinary source files, so the rare naming loses to the common one and the rule says why.
  • A test whose verdict depends on ambient environment is a false-red generator — and the recorded diagnosis of one is worth re-measuring before you fix it. One case in the installer suite reported fail in a bare shell and pass under an explicit character encoding, so its answer depended on how the terminal happened to be configured rather than on the code. The recorded explanation was "the search tool aborts in a non-UTF-8 locale", which sounds complete and suggests an obvious fix: pin the locale to the portable default. Measuring first killed that fix. The portable default is non-UTF-8, and it aborts too — the crash happens in every single-byte locale and only a UTF-8 one survives, so the obvious pin would have changed nothing while looking like a repair. The same measurement turned up a second defect hiding underneath: the case-insensitive flag was doing real work, because the live file capitalises the phrase being searched for, so a "tidier" case-sensitive version reports not-found and fails the case for an entirely unrelated reason. Both went away by deleting the external tool call and using the shell's own pattern matching — no subprocess, no locale, the same move that made the guards fast. The general form: pinning an environment around a bug leaves the bug, one machine away from breaking again. Prefer removing the dependency to configuring it. And a second case in the same suite had simply rotted — it asserted an exact count of registered gates, which was true when written and false the moment a second gate was legitimately added, so it reported failure for two sessions while the installer behaved correctly. It now compares before against after, which cannot rot, because the invariant was never the number: it was that the installer does not change it.
  • When a rule cannot be compiled, that is sometimes the correct answer — and a triage that forgets it will delete the judgment layer to improve a ratio. The audit's instruction for the 199 unenforced rules was binary: each is worth a check or worth deleting, and one that is neither is dead weight. The decision it cited to justify that ends with the opposite sentence — prose is reserved for judgment a check cannot make — and both operating manuals open by saying the same thing. "Push back with data, not opinion" is not compilable and is not dead weight. Applying the binary literally would have emptied the manual of the only thing it exists to hold: the metric eating the thing it measures. Two further corrections came out of the pass. First, the findings list was four days stale: of its seven highest-consequence unenforced rules, four had already closed, three of them by mechanisms built after it was written — so a confident verdict on each would have been a confident verdict about a world that had moved. A findings list is a measurement, and measurements expire. Second, nothing was deleted, and that was the finding rather than a dodge: the rows that looked like dead weight turned out to be judgment, already closed, or cheap enough that building the check beat arguing about it — the genuine dead weight having been cut by earlier work before this pass ever reached it.
  • A check built from the code alone will flag what a recorded decision already settled — and knowing that is not the same as being immune to it. A check was written asserting that a disabled configuration flag had switched off the only executor for the two-pass review rule. It went red on its first run, correctly by its own logic and wrongly in fact: the flag was a deliberate choice, recorded months earlier and verified against the plugin's source, that disables one narrow review while the mechanisms actually carrying the rule stay on. The gap was plainly visible in the configuration; the reason it had been left open lived in a session journal that no check reads. What makes this worth recording is that it happened in the same session that had just re-read the lesson and written it into a commit message. The rule survives the embarrassment intact and is slightly sharper for it: read the decision record for the area before building the check, not after it goes red. The cost here was a single run, and only because the record was consulted before the finding was reported as real.
  • Read the decision log for the area before writing the plan, not while executing it. A plan assembled from the code proposed adding a pattern to a config deny-list that an earlier recorded decision had considered and deliberately refused, because config patterns have no negation and the pattern would also block the committed templates the code layer allows and can except. The gap was visible in the code. The reason it had been left open was not. So the plan read as sensible hardening right up to the moment the decision was found, which happened by luck. A missing rule has two causes that look identical from the source: nobody thought of it, or somebody thought about it and said no — and only the second is written down, somewhere the code does not point at. There is a cheaper catch for the same class that needs no external file: the same plan also added those paths as must-allow test cases, so it contradicted itself within one document. If a plan adds a must-allow case and a deny rule covering the same paths, one of them is wrong.
  • scripts/hook-tests/canary-test.sh 39 cases covering the mirror comparisons, and the reason it exists is that the check which is itself the safety net had no test of its own. It caught a real defect on the day it was written. The new comparison identified files by their path rather than their name, and the checksum tool on this machine prefixes each filename with a marker character. Left in place, every lookup missed, so the check reported no differences because it had compared nothing. The two older comparisons were immune by pure accident: they identify files by name, and the step that strips the folder path removes the marker along with it. So the pattern being copied looked proven, and the property that made it safe was not the property being copied. Only the cases where two files genuinely differed failed. Every case where a file was simply missing passed, because absence and difference run through different code. The lesson generalises past this setup: when testing a comparison, include a case where two things differ, not only a case where one is absent.
  • A commit proves the repository's state. It never proves what is running. This is the most useful thing the setup has learned about itself, and it cost a near-miss to learn. Before starting a session of hook work, the committed suite was run against the live hooks as a baseline — and returned 97 of 120. A guard fix that a commit had recorded as shipped was never installed: it sat in a backups folder while the older file stayed live, leaving eleven secret-leak checks and six destructive-delete checks silently unenforced. Reading the file would have passed. Grepping its source would have passed. Trusting the commit log would have passed. Only feeding a payload to the hook that was actually loaded caught it. The forensics matter as much as the finding: the commit did not lie — a timestamped backup proves the fix was genuinely installed fifty seconds before it — the rollback came seventy minutes later, and a subsequent commit then recorded a green gate against the reverted file. Why the rollback happened could not be established, and was left recorded as unproven rather than guessed at, because a plausible reconstruction written into a journal becomes a fact the next reader inherits.
  • docs/ENFORCEMENT.md + scripts/enforcement-check.sh The comparator for the thesis itself. An audit of this setup found that of 225 standing rules, ten had anything that actually executed them — and that every remediation item which shipped an executor closed, while every one that stayed prose rotted. The obvious response is a table listing which rules are genuinely enforced and by what. The non-obvious part is that such a table is prose the moment nobody checks it, and would decay exactly like the rules it describes while reading as proof that it had not. So the table names, for each enforced rule, the precise file that enforces it, and a check resolves every one of those paths at session start. What it verifies is deliberately weak: not that a guard still works — the payload suites do that — but that the guard still exists. That is the gap the suites structurally cannot see, and it has opened twice here: a repaired guard left in a backups folder while the broken copy stayed live, and two skills sitting uninstalled while a command called one of them by name. A row whose executor cell is prose rather than a path is rejected, not skipped, because silently skipping the rows you cannot parse is how a table drifts into decoration while still reporting clean. One detail worth keeping: the first version took five seconds for twenty-nine rows because it forked two helper processes per row. Against a session-start budget already two-thirds spent that is not a slow check, it is a broken one; rewritten with the shell's own string handling it takes four-tenths of a second for an identical verdict. The parsing was never the cost. The forking was.
  • scripts/gates/ Two phase gates that were prose, compiled. The deployment gate ends a project with "all seven conditions confirmed" — seven lines a person reads and ticks. Four of those seven are claims about the live internet: the site is reachable, health checks answer, a funnel is queryable, a rollback was rehearsed and timed. A script cannot know any of that, and one that guessed would be worse than none, because it converts an open question into a false answer. So the gate splits them: artifact conditions are checked mechanically, and live-system conditions must be ticked with evidence — a URL, a path, or a timing. A bare tick is rejected, which is what the command's own first line always demanded and nothing enforced. The gate also refuses to run at all if the seven conditions have drifted apart across the three files that carry them, kept in step until now by a comment politely asking whoever edits one to edit all three. Three copies and a request is the shape of every drift in this setup's history. The design gate is the same discipline applied to accessibility: it enforces the checks decidable from the file, reports one as necessary-but-not-sufficient, and refuses to judge contrast and viewport rendering at all, printing them as outstanding on every run including passes. The step's own wording is "never asserted", and a gate that falls silent having checked four of six teaches the reader that six were checked.
  • scripts/stale-doc-check.sh and scripts/forbidden-patterns-check.sh Two sweeps turned into checks, because a sweep is a one-time act. The first pins facts that were true and stopped being true — a phase count that grew, a kill criterion routing to a retired framework, a file path that moved — against the live documents only, with historical records structurally out of scope so that no dated snapshot is ever rewritten to satisfy a grep. It found a miss in the very sweep that preceded it, in prose the manual read had skimmed past. The second compiles the mechanically checkable half of the forbidden-patterns list, including the operating manual's own hard line cap, which was sitting at exactly its stated maximum with nothing watching — one more line and the file would have broken its own first rule silently. Both split by false-positive risk rather than by topic: the deterministic half runs every session, the half that greps real source code runs at the deployment gate where a human is already reading output. A check that cries wolf at every session start is one that gets routed around, and that is a documented failure here, not a hypothetical.
  • scripts/obsidian-snapshot.sh The wrap-up command overwrites the Obsidian project page wholesale, and step one of that procedure is to snapshot the existing page first as rollback insurance. That step was prose only — a copy command typed by hand. On a day with three sessions, the second session's snapshot silently overwrote the first's, because the naming scheme assumed one snapshot per day. The rollback insurance destroyed the thing it was insuring, and it had to be recovered from a commit afterwards. This is that step as an executor: it refuses to overwrite an existing snapshot and takes a numbered suffix on a same-day collision, which is the identical rule the live-versus-committed comparator already uses for the same reason — so a reader who learns one naming scheme knows both. The suffix is highest-plus-one, not first-free, and that distinction is load-bearing: with number two deleted and number three present, taking the lowest free slot makes the newest snapshot sort before an older one, breaking the invariant that name order equals time order. That exact failure happened for real, minutes after the first version was written. Gaps in the numbering are honest; going backwards is not. It also verifies the copied bytes against the source and refuses loudly if the source is missing, because a wrap-up that continues on a failed snapshot overwrites the live page believing insurance exists.
  • scripts/verify-live-vs-mirror.sh The durable answer to the above, and it takes about a second. Every hook and settings file is mirrored into the repository alongside a MANIFEST.sha256, and this script compares the live files against those hashes: exit 0 when they match, exit 1 naming the file that drifted. It is verified to bite, not merely to pass — pointed at a decoy directory holding the regressed guard, it reports the drift and fails. Run it at the start of any session that touches enforcement. The general principle is worth more than the script: for anything where the deployed copy can diverge from the committed copy, build the one-command diff before you need it, because the gap between them is invisible by construction and nobody goes looking for an invisible gap.

    Then it cried wolf, one session after being built. On its first unattended run it reported three drifts, and all three were the mirror being out of date rather than the live files being wrong: a hook had gained a line in a commit that never refreshed the snapshot, and two settings files still held entries for a tool that had been retired. Enforcement was intact the whole time, while the artefact built to prove that printed "do not trust the enforcement layer". A false alarm is not a lesser failure than a false pass — both end in the signal being ignored, which is precisely how the earlier fail-opens survived. The root cause was that nothing regenerated the manifest: it was written by hand once, so staying correct depended on a person remembering an undocumented step. The fix was not copying the three files again. It was deleting the human step, via a --new-snapshot YYYY-MM-DD mode that copies live into a new dated folder, rewrites the manifest, and verifies it in the same run. It refuses to overwrite an existing dated folder, because a dated record that gets rewritten lies about itself, and it fails before writing anything if a listed source is missing, because a partial snapshot verifies clean while covering less. The durable rule: when you add a check, ask what regenerates its expected values. If the answer is a person, the check has a second failure mode as bad as the one it covers. Same pass found that a file the checker itself depended on was absent from its own manifest — cover the check's dependencies, not just its targets.
  • The bypass this closed. Two independent mechanisms, both live. Four permission entries auto-approved powershell and cmd invocations from the shell — they reached the guard, but every check was written in bash syntax, so a PowerShell destructive command passed through unmatched. Separately, the PowerShell tool is a different tool entirely and was named in no hook matcher, so it was never inspected at all. Widening the matcher without first making the guard understand PowerShell would have been theatre; removing the permission entries without either would have moved the hole rather than closed it. All three had to land, in that order.
  • A rule closes only when something runs it, and this is now measured rather than believed. A full audit of the setup ran twice, three days apart, and the second one reconciled the first claim by claim. The result is the strongest argument this page can make for its own approach. Of the twenty items the first audit raised, every one whose fix included something that runs closed: seven out of seven. Of the thirteen that were written down as a rule or left to a person to remember, three closed. Every item still open is a written one, and not a single one of the automated ones is open. Measured across the whole setup rather than one audit, ten of two hundred and twenty-five standing rules have anything that actually enforces them, and those ten come down to five mechanisms. The sharpest detail: the first audit narrowed one check to a single surface, and that narrowness produced the next three failures on its own. The conclusion is uncomfortable and worth keeping. Writing a rule down feels like closing the issue and almost never is, so the next round of work builds checks, not more rules. A rule that cannot be turned into a check is either worth deleting or worth admitting is a hope.
  • Deleting allow entries does not close a permission hole — ask does. The four entries were removed from settings.json and the bypass stayed open, because settings.local.json re-granted powershell.exe outright plus a prefix wildcard covering any double-quoted PowerShell command, and the project's own local settings added a third. settings.json is not the only grant surface; enumerate every layer before calling a bypass closed. The durable fix is the rule type, not the cleanup: documented precedence is deny → ask → allow, first match wins, and an ask rule prompts even when a more specific allow matches, at any scope — so no future session's one-off approval can silently reopen it. Deleting grants is inherently leaky, because every approval writes a fresh one. The same mechanism closed a confirmed MCP deploy bypass (an MCP tool call is not a Bash command, so no shell guard ever saw it) with a single ask entry and no new hook — when configuration already expresses the policy, do not build a hook to express it again. The same mechanism was then turned on the setup's own contradictions. The operating manual said overwriting files and changing the remote VM were confirm-first, while the settings granted an unrestricted write permission and blanket ssh/scp — and the config, not the prose, is what actually runs. Both moved to ask, along with four command wildcards with real blast radius (killing processes, renaming files, creating files, installing packages) out of thirteen; the other nine are read-only and stayed. Two details worth carrying: the remote-access grants existed in two settings files, so removing them from one would have changed nothing — enumerate every layer — and an exact-string allow still outranks a wildcard ask, so one narrow read-only entry deliberately survives the change and is documented rather than quietly removed.
  • A caveat that invalidates a whole class of test. None of this prompting behaviour can be verified from inside a session running with permissions auto-accepted — commands granted by no settings file still run unprompted there. Any check whose pass condition is "this should now prompt" must be reported as inconclusive in such a session, never as passed. Confirm the permission posture before designing the test, not after. And "auto-accept" is too coarse a description to reason with. A later session turned out to be mixed: routine commands granted by no settings file ran unprompted, while a classifier hard-blocked every write into the configuration directory outright. A mixed posture is evidence in neither direction — it neither confirms a rule prompts nor confirms it does not. The useful consequence was procedural rather than technical: when writes to a protected directory are refused, the correct response is to hand the human a single batched command with the expected checksums and let them run it, not to reach the same end state through a tool the block did not name. Routing around a guard that just fired is not an alternative approach; it is the thing the guard exists to stop.

External model delegation
  • /delegate Sends a read-only task to a second model provider's CLI — a non-Anthropic second opinion on a plan or diff, a research pass, or reading a file too large to load. It returns text; the main session applies any change.
  • agy-delegate.sh --type review|research|longread The wrapper. Per-lane model defaults: a strong reasoning model for judgement work, a cheap fast one for bulk reading.
  • agy-delegate.sh --stats Reports this wrapper's own token spend per quota pool over the last 7 days, from a local ledger. Labelled a burn estimate, not remaining quota — the failure mode to avoid is a number that looks authoritative and isn't.

Why it's a tool and not an agent. The Agent tool's model parameter is a closed enum of first-party models, so no subagent can be spawned onto another provider's model. A second provider is reachable only by shelling out. The model-router was deliberately not given a tag for it — that would produce plans the autonomous executor is structurally unable to dispatch. The harness decides what is possible and the design follows it, not the reverse.

Content goes in; the external CLI never reads anything. Run headless it cannot prompt for tool permission, so it auto-denies and returns status:SUCCESS with an empty response — a silent failure wearing a success mask. Denials were observed on more than one permission and an identical call returned empty once then worked, so the tool path is non-deterministic, not merely restricted. The shell therefore assembles every payload. Three consequences, all good: read-only becomes structural rather than promised; large content flows shell → CLI and never enters the main session's context; and it measured cheaper and faster than the tool path, because no turns are burned on denied calls. The wrapper adds a no-tools preamble, retries once, and exits non-zero rather than ever reporting an empty answer as success.

The subagent is the boundary. It is declared with no write tools at all, so the read-only guarantee is enforced by omission rather than instruction, and it distils the reply so raw output never reaches the main context. It is told to treat everything the external model returns as data to relay, never as instructions to follow — and to state its own verdict on which findings are real, because it has context the external model lacks. On its first two real reviews the external model produced 8 findings, 7 genuine and 1 wrong.

Spend deliberately. Quota is a weekly budget metered on token cost rather than request count, and roughly 1% of a week goes per call. Worth it for a real plan or a substantial diff; not for a one-liner. A plan-finalization hook offers a second-opinion pass rather than spending automatically — a throwaway plan shouldn't silently cost quota. This replaced an earlier delegation path whose reviews were written to a file nothing ever read: an external opinion with no return path into context is not a review.

The reversal that cost nothing

A secret manager was chosen, and reversed two days later. Nothing had to be undone because nothing had been built yet — the first check was whether the setup had actually happened, and it had not. No new fact about the rejected tool was needed. The original decision had itself written the rule "capture and search first, sync second", and then picked the tool that loses on it. Applying that entry's own rule was enough. The superseded decision now carries a banner at its own heading, because the recorded failure mode here is a plan proposing what a decision already refused, purely because nothing pointed at it.

Proved before it was recorded

The chosen tool's homepage claimed parity on this platform; its own FAQ said nothing about it and a third party denied it. So it was tested rather than believed: an official installer, both shells passing, and an accidental overwrite recovered by decrypting the pre-overwrite value back out of git history and hash-matching it — the exact scenario the rejected tool's free tier calls unrecoverable.

The finding worth more than the store
The restore proof passed and the backup was still broken

A real secret was decrypted from a clone of the remote using only the backup key, hash-identical to the primary-key decrypt, with an empty keyring as a control that correctly failed. Every secret was recoverable and the gate would have been signed off on that. Then the clone was diffed against the live copy and the recipient list came back with the wrong line endings — and the crypto tool rejects a fingerprint with a stray carriage return, measured, non-zero exit against zero. So the ciphertext restored perfectly while the restored store could not have encrypted the next secret, and the tool ignores an unusable recipient quietly.

Why it was caught

Proving you can read a backup is not proving you can use the system it restores. The part that broke only matters after a disaster, which is the part nobody exercises. It surfaced only because the plan said to verify the remote by cloning it back and diffing, rather than by reading the push output — and a push that reports success says nothing about whether a checkout of it works. Fourth instance of this line-ending class here; every previous fix was scoped to the files in front of it, so the standing question is now whether the global setting should change rather than be patched a fifth time.

A documented path was corrupted by the tool that wrote it

The setup sheet carried a raw control character inside a path, sitting in the block explicitly labelled do not re-derive — the highest-trust prose in the repo, written specifically to stop the next session checking for itself. It was not a typo. A stream editor's replacement text interprets backslash escapes, so writing a Windows path through a substitution turns the folder separator plus certain letters into control characters, silently. Three attempts to fix it failed in three different ways that all looked identical from outside — one language reported the write as successful and changed nothing on disk, two others never matched the pattern at all and exited zero. What generalises: read the value back as bytes, or you are checking the renderer and not the file.

The migration tool, and the two rules it is built on
  • It never prints a value. Not on success, not in an error, not in a preview. Errors name the key and the line number. A migrator that echoes a credential into a terminal scrollback has defeated the store it fills.
  • It refuses rather than guesses. The whole file is parsed and every conflict checked before the first write, so a bad line late in a file cannot leave the earlier ones migrated. A partially migrated project is worse than an untouched one, because it looks done.
  • An ambiguous value that a conventional parser would silently truncate is refused instead, because truncating a secret is a corruption with no tell.
  • An empty result is a refusal, not a success. "Zero migrated, exit 0" is the self-reported-success shape this setup has been burned by three separate times.
  • A skip instruction naming something not present is refused, because a rotted skip and a deliberate one look identical from outside.
Verified, not assumed

Its suite was falsified with two deliberately broken stand-ins before being trusted — one that always succeeds and one that always refuses, producing 27 and 36 failures respectively against zero for the real thing. Every refusal case additionally asserts that nothing was written, not merely that the exit code was right. The suite was registered with the whole-suite runner and the runner's discovery floor raised in the same change, because adding a member to a checked set is part of the change, not follow-up work.
