Purpose

Turn a raw idea into a PRD.md that survives scrutiny — before a framework is chosen. Both Blueprint and Builder OS consume the PRD, so writing it can't live inside either one.

Method

A 6-stage state machine (/prd-create). Divergence happens before any research question is written, and those questions are git-committed before narrowing is allowed — so the answer can't be reverse-engineered from the desired conclusion.

Purpose

Derive a design language from what the product must prove, rather than applying an aesthetic on top of it. The test: if the design language could be moved to a different product without feeling wrong, it was imposed, not derived.

Method

Seven stages, data before pixels. Tool choices are settled by decision matrices, not preference — and design tokens are never carried over from a previous project.

A fresh-context overnight loop was evaluated and declined. The available implementation needs a hand-patch to its own cached config that any update silently wipes, never varies its prompt between iterations, and its completion signal is a single exact-string match — so it cannot express "finished" versus "blocked."

Guardrails (hooks — fire without being called)
  • pre-tool-use-guard blocks force-push, --no-verify, home-dir deletes, secret echoing
  • deploy-preflight-guard blocks deploys unless the project records a deploy target
  • plan-finalized-nudge reminds, the moment a plan is approved or written, to offer the autonomous-execution pipeline
  • framework-state-check flags an unlocked framework or a stalled PRD run at boot
  • prompt-compile classifies each prompt and compiles a task brief before medium/high-stakes work
  • security-guidance pattern warnings on every edit (regex, no model call); the diff review on stop is off, the agentic reviewer on git commit is on
  • claude-security deep scan, on demand only — pairs with a history scanner, since a working-tree scan cannot see a credential that was committed and later deleted

Purpose

Development moved out of an editor's integrated terminal and back into a raw one — Windows Terminal + PowerShell 7, nothing else.

Method

Every piece is either a standalone binary in a personal bin folder or a module installed -Scope CurrentUser. Nothing requires admin rights or touches a system-wide install.

What's wired in
  • proj / z fuzzy project picker for browsing; frecency jump for the daily repos
  • mdview / bat readable Markdown and syntax-highlighted files, in-terminal
  • delta every git diff and git log -p rendered side-by-side — no new commands to learn
  • Ctrl+R / Ctrl+T fuzzy history search and fuzzy path insertion, wired into the shell itself
  • Win + ` quake-mode terminal drops down over any app
  • Starship + Nerd Font git status and language versions in the prompt, no per-project config
Cross-window notifications

Running several Claude Code sessions in parallel means missing the one that's gone idle waiting for input. Claude Code's Notification hook fires a real Windows toast titled with the project folder — so it's obvious which window to switch to.

Known limitation
Ctrl+V image paste is broken on native WindowsDocumented as supported, but silently fails outside WSL — an upstream bug, not local config. Workaround: save the screenshot, then drag the file in.

Why this page exists

This is disaster-recovery material. If the setup has to be rebuilt on another machine or another account, the git repo plus this page is what makes that possible — which is why the sync is a standing rule rather than a nice-to-have, and why no credential ever appears here.

The setup is versioned, because a setup is a system and systems drift. A version is a point-in-time inventory of both halves — this framework repo and the global ~/.claude/ config — so any past state can be described, compared, and restored. Setup and Playbook answer what and when. This tab answers how it got here, including where it is currently inconsistent.

Why version a config at allSession journals record changes and git log records one repo. Neither answers "what did my whole setup look like on this date" — and only one of the two halves is under git. A version is cut when the shape changes (a framework, hook, skill, agent, command, plugin, or vendored release), not on every edit.

/prd-create is a 6-stage state machine that produces PRD.md with a Provenance block, which /rubric then requires and cites for each of its 5 answers.

Ground rules — apply to every stage
Gaurav owns the problemClaude never invents or assumes the idea, pain point, or problem statement — only surfaces, refines, and pressure-tests what Gaurav gives it.
2–3 options, alwaysEvery decision point offers real alternatives with tradeoffs. Never a single unilateral call.
Research stays separatePRIMARY_RESEARCH.md and SECONDARY_RESEARCH.md are never merged, and never folded into the PRD as first-draft prose — the PRD cites them.
Broad before narrowNever assume a problem statement and research backward to justify it. Divergence happens before any research question is written.
Stage detail
A
Spark
Gaurav dumps the raw idea in whatever form it comes. Claude asks clarifying questions one at a time — never reframes or narrows. Captured near-verbatim into SPARK.md. Everything defaults to 🔵 hypothesis.
B
Problem-space map
≥3 distinct framings, including one mandatory anti-thesis framing — the version where this isn't worth solving, or the pain is adjacent. Gaurav does not pick yet; the output is a research agenda, not a decision. Gate: "Framings approved."
C
Research — bias lock
Questions are derived from all Stage B framings and committed to git before any narrowing is allowed — the actual lock, not an honor system. PRIMARY_RESEARCH.md holds interview scripts and transcripts (no 🟢 tag anywhere without a quotable line here); SECONDARY_RESEARCH.md holds the market scan as a Steal List. Both require an Evidence Against section with ≥3 entries, or an explicit "found nothing" log. Fast path: experiment-brief.md gets a ~30-min secondary-only sweep — an all-🔵/🟡 brief is the expected shape, not a failure.
D
Narrow
Problem clustering → P1→P2→P3→core-failure chain → 2–3 candidate statements, each with supporting and contradicting evidence cited by file anchor, plus "what evidence would flip this." Gaurav finalizes the wording; Claude only builds the evidence dossier. Gate: "Problem statement finalized."
E
Template select + draft
Every claim carries a confidence tag plus a reference into the research files — the PRD cites research, it doesn't restate it. Also required: every success criterion rewritten into falsifiable form, and the Prior Art & Steal List carried forward to Blueprint P0.
F
Grill + seal
grill-me targets the discovery chain specifically: "which Stage B framing did the research actually kill?" If the answer is "none," that's surfaced as a smell, not silently passed. Survivors seal into PRD.md with a Provenance block — template used, stakes classification, research refs, grill date. Gate: "PRD approved" → /rubric.
The four templates

Rubric requires PRD.md to exist and cites it for every answer — it refuses to run on a vacuum idea.

Phase detail
P0
PRD Intake
Read PRD → 5-bullet read-back → falsifiable success criteria → ambiguity list → Prior Art steal list. Steelman gate: state the polarizing claim, give the sharpest counter in two sentences, defend in two. If the defense doesn't hold, revisit scope before P1. Provenance short-circuit: if the PRD already carries a Provenance block, steps 2–5 are read from it rather than regenerated — P0 becomes a confirmation gate, not a repeat. Gate: "Read-back approved."
P1
Solution Stage
POT-format interview (Proposal → Options → Tell me). Eight topics in order: core journey, MVP features, non-goals, tech shape, third-party services, metrics, recruiter signal, risk register. One session, max 10 questions. Gate: "Solution approved."
P2
Design
Runs the 7-stage Design Framework. Required artifact from Stage 1: Named Reader — one specific real person this product must land for, stored in brand-guide.md. Gate: "Spec approved."
P3
Implementation Plan
Slice 0 is the walking skeleton: frontend shell + /health + DB + PostHog + Sentry + docs stub. Remaining slices ordered by risk; each is one capability plus tests, analytics, and a HOW_TO_USE section. model-router runs before the gate, so every step carries a model tag. Gate: "Plan approved."
P4
Development
Per slice: Red (failing tests, mandatory — no skipping to Green) → Green → Refactor → Instrument → Document → Review → Smoke-run → Commit. Between slices: a 5-line PROGRESS.md update and /compact. Gate: all tests green, HOW_TO_USE complete.
P5
Testing
Layer 0 security (IDOR, authz, input sanitization) · Layer 1 unit + integration + E2E · Layer 2 the 8-category edge-case checklist · Layer 3 acceptance criteria. Gate: CI green, zero P0/P1 bugs, acceptance criteria walked.
P6
Deployment
13 items: env vars, secrets, /health, migrations, PostHog, Sentry, HTTPS, CORS, rate limits, backups, CI, README, CASE_STUDY.md. Post-deploy: a Playwright smoke test against the live URL — light/dark/mobile screenshots, zero console errors, zero failed requests. Gate: Definition of Shipped, 7 conditions confirmed.

What v0.4.0 added, not yet wired in
  • ERD An engineering spec between PRD and build: schema, API contract, and a chunk map with boundary contracts. Its core discipline is one starred structural decision, reviewed first — the single call that forces a rewrite if wrong, stated and evidenced before any code. The judged-most-valuable piece of the whole update.
  • postmortem Scores results against the PRD's original success criteria, states one lesson as a rule, and forces an explicit Iterate / Scale / Retire call. Fills a real hole: the criteria were being authored and never scored.
  • sessions Mode-aware. The extends-existing arc skips scaffold, landing and auth setup, and builds chunk-by-chunk against the ERD — which the old linear arc handled badly, and which is what most real work actually looks like.
  • discovery Overlaps /prd-create, which is stricter. Likely to stay unused.

Guardrail hooks
  • pre-tool-use-guard.sh Blocks git push --force, --no-verify, home-directory rm -rf, reset-and-push chains, echoing secret-shaped vars to output, python3 where only python exists, and quoted Windows paths with the trailing-backslash bug that breaks bash parsing. Rewritten pure bash after the same fail-open class was found here too — the third instance. It parsed the payload through an interpreter and emitted its deny from an interpreter heredoc; on this machine that interpreter resolves only to an unrelated third-party virtualenv, so the gate would have silently allowed every forbidden pattern the moment that venv moved. Proven, not argued: under a PATH with the interpreter removed, the old hook returned empty output and exit 0 — allow — for a force-push; the rewrite denies. Three further changes came out of it. It now fails closed: a payload carrying a command it cannot parse is denied, where the old code treated an unreadable command as nothing to check. Its extraction no longer uses the greedy pattern the deploy guard still carries, so sibling fields in the payload cannot leak into the command being judged. And it covers PowerShell shapes — Remove-Item -Recurse -Force on home or a drive root, $env: secret variables, and git flags smuggled through powershell -c or cmd /c wrappers, which no bash-syntax regex had ever matched. The secret check was also tightened to require a real variable reference rather than a bare English word, after it blocked a legitimate echo of a section heading — a gate that cries wolf gets routed around, which is its own kind of failure. Then the same failure mode appeared twice more, and it is the important one: the guard could not tell a forbidden pattern being executed from one being mentioned. It denied a git commit whose message described a force-push, and denied a jq filter that merely named a permission entry, because the ( inside a quoted string read as a command position. In a setup whose whole purpose is documenting its own guardrails, that is not an edge case. Commit message bodies are now scrubbed before the checks run — non-greedy, so a command chained after the message stays in the checked string, and an early-closed quote fails closed. Also added: printenv, PowerShell Env: read paths, and the console.log/puts/System.out.println family of output verbs; cmd-shape recursive deletes (rd /s /q); and backtick-escaped Windows paths. One extension was refused: matching secrets across a pipe, because every formulation of it also denied a routine authenticated curl … | tee, which never prints the value. The motivating leak was solved by widening the verb vocabulary instead of the structural scope — prefer that trade every time.
  • deploy-preflight-guard.sh Blocks vercel --prod and railway up unless the target project's CLAUDE.md records a Deploy target: line — preventing a deploy to the wrong account by construction. Rewritten after being found broken in both directions: it had been resolving CLAUDE.md against the hook's own working directory rather than the project being deployed (so it blocked every deploy), it never JSON-unescaped the command (so a quoted cd path parsed as garbage), and it parsed via an interpreter with 2>/dev/null — meaning a missing interpreter made it exit 0 and allow the deploy. Now pure bash with no interpreter dependency, and a 13-case suite asserting allow and deny. The general rule it produced: a gate must fail closed when its own dependencies are absent, and needs a functional test, because a guard that never fires and a guard that always fires look identical from outside. Still open: those 13 cases lived only in session memory until they were persisted into the harness below, and persisting them exposed a fourth defect that is not yet fixed — the command is extracted with a greedy pattern that captures through to the last quote on the line, so the payload's description becomes part of the command. A description containing the words "cd into…" makes the guard resolve the wrong directory and block a correctly-documented project. Same failure as its original bug #1, reached by a different route, and a reminder that fixing a hook is not the same as fixing the parsing it shares with every other hook.
  • plan-finalized-nudge.sh A PostToolUse hook on Write|ExitPlanMode that fires the moment a plan is finalized — plan mode approved, or a plan file written to a plans/ directory — and injects a reminder to offer the model-routing → autonomous-execution pipeline, which is easy to forget at exactly that moment. Correctly fail-open (a missed reminder is harmless; that same idiom in a gate is a bug). Verified firing; its real failure mode is the injected context being read past rather than acted on, which no code change fixes.
  • framework-state-check.sh Flags an unlocked framework or a stalled /prd-create run at session boot.
  • prompt-compile (v60samurai/agent-skills) A deterministic bash UserPromptSubmit hook that classifies every prompt into low/medium/high bands — no LLM self-grading — paired with a skill that compiles a 7-section task brief before medium and high band work executes. High band waits for approval; medium shows the brief and proceeds; bug reports and explicit escape hatches stay silent.
  • security-guidance Runs at commit-only posture, which is a deliberate configuration rather than the default. Three layers ship: regex pattern warnings on every edit (no model call, no cost), an LLM diff review on session stop, and an agentic reviewer on git commit. The stop review is disabled — it is the expensive layer and the one most likely to fire on work that was never going to be committed. The other two keep their own independent gates and stay on. Worth knowing when rebuilding: the flag is read at module import and injected at session start, so it takes effect from the next session, not the one that sets it.
  • claude-security A multi-agent scan invoked on demand, never automatically. It scans the working tree, which leaves a real gap: a credential committed and later deleted stays in history and remains readable in any public repo. Pair it with a dedicated history scanner run in redacting mode, so the report carries rule, file, commit, and line but never the value itself — safe by construction rather than by intent.
Gate testing
  • scripts/hook-tests/run.sh The answer to "how do you know a guardrail works." 71 functional cases, pure bash plus jq, each piping a realistically-shaped payload into a real hook on stdin and asserting its actual output and exit code. Existence checks do not count — "is the hook present and registered?" passes a hook that is broken in code and a hook whose output nobody reads, which is exactly how two separate defects survived an audit. Every gate ships at least one allow case and one deny case, because proving a guard fires is only half of it; proving it stays quiet on legitimate work is what stops it being disabled. Three properties earn their keep: the runner aborts if any declared case went unscored, so a suite can never report green having tested nothing; the hook path is overridable, so a candidate rewrite is tested standalone before it is swapped into a live session; and a case can run under a modified PATH, which is how the interpreter-dependency fail-open is proven closed rather than assumed. Falsified deliberately in both directions — pointed at an always-allow stub, every deny case fails; pointed at an always-deny stub, every allow case fails. A suite that cannot fail proves nothing.
  • The bypass this closed. Two independent mechanisms, both live. Four permission entries auto-approved powershell and cmd invocations from the shell — they reached the guard, but every check was written in bash syntax, so a PowerShell destructive command passed through unmatched. Separately, the PowerShell tool is a different tool entirely and was named in no hook matcher, so it was never inspected at all. Widening the matcher without first making the guard understand PowerShell would have been theatre; removing the permission entries without either would have moved the hole rather than closed it. All three had to land, in that order.
  • Deleting allow entries does not close a permission hole — ask does. The four entries were removed from settings.json and the bypass stayed open, because settings.local.json re-granted powershell.exe outright plus a prefix wildcard covering any double-quoted PowerShell command, and the project's own local settings added a third. settings.json is not the only grant surface; enumerate every layer before calling a bypass closed. The durable fix is the rule type, not the cleanup: documented precedence is deny → ask → allow, first match wins, and an ask rule prompts even when a more specific allow matches, at any scope — so no future session's one-off approval can silently reopen it. Deleting grants is inherently leaky, because every approval writes a fresh one. The same mechanism closed a confirmed MCP deploy bypass (an MCP tool call is not a Bash command, so no shell guard ever saw it) with a single ask entry and no new hook — when configuration already expresses the policy, do not build a hook to express it again.
  • A caveat that invalidates a whole class of test. None of this prompting behaviour can be verified from inside a session running with permissions auto-accepted — commands granted by no settings file still run unprompted there. Any check whose pass condition is "this should now prompt" must be reported as inconclusive in such a session, never as passed. Confirm the permission posture before designing the test, not after.

Stack

Stack is project-specific, not a global default — recorded in each project's own CLAUDE.md "Framework state" block. A new project checks sibling memory/project.md files for a precedent before picking one from scratch; Gaurav confirms, and it locks for that project. One gotcha stays global regardless of stack: pyairtable and anthropic SDKs are sync — never await them.

Analytics is the one global exception. Every deployed web project reports into a single shared analytics project and must register a project: <folder-name> super-property — that property, never the hostname, is how one dashboard separates every site (hostnames fragment across preview URLs, custom domains and IP hosts). Default depth is anonymous pageviews only: no autocapture, no identify() on public sites, so no consent banner. Shipped as a drop-in analytics.js — one file, one script tag, no npm dependency — because the alternative was ten bespoke SDK integrations across three frameworks, each touching a lockfile. It cannot break a build and behaves identically on static HTML, Next.js and Vite. Added after an audit found four different analytics states across ~20 projects and no unified view; the failure was the absence of a default, not the tooling.

Think → Build → Prove

Load context — memory folder, project CLAUDE.md. What was tried before? What failed?
Challenge the ask — right problem, right solution, right time? "Will we regret this in 3 months?"
Map the system — boundaries, data flows, failure modes. Integration seams are where bugs live.
Plan — 3+ steps means plan mode. Lock the plan, flip to auto-accept, execute in one pass; stop hand-holding mid-build. Non-trivial work writes a failing test first.
Build in stages — parallel subagents for independent work; a git worktree when concurrent sessions share a repo. If prediction and reality diverge, investigate immediately.
Prove — the self-check gate, then record what surprised you and what pattern prevents this class of problem.

Cross-window notifications
Why this existsRunning several Claude Code sessions in parallel windows means missing the moment one goes idle waiting for a permission prompt — no signal short of alt-tabbing through every window.

Solved with Claude Code's own Notification hook, which fires with message, cwd, and notification type on stdin whenever the agent needs input. Registered globally with matcher permission_prompt|idle_prompt, calling a small PowerShell script that fires a real Windows toast via BurntToast. The title shows Claude Code — <project folder>, so it's clear which window to switch to without opening any of them.

Known limitation — not solved
Ctrl+V image paste is genuinely broken on native WindowsClaude Code documents clipboard-image paste as supported, but on native Windows (not WSL) it silently fails — confirmed via multiple open upstream issues, not a local config problem. No keybinding fix exists; it's inside Claude Code's own Windows clipboard-reading code. Workaround: save the screenshot to a file, then drag it into the prompt or paste its path.
