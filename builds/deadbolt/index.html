Private tool Build 03 · Nov 2026

Deadbolt

Guard hooks for Claude Code that block a short list of risky commands. A canary runs at every session start and warns me if a guard stops saying no.

I built it for my own machine, after my guards failed silently more than once. The repo stays private. This page shows how it has done, with the weak numbers left in.

What it blocked

The guards keep no log, so I counted blocks from my Claude Code session files. Those files go back about 30 days. The raw search found 1,623 matching lines. Retries and subagent copies repeat the same block, so I kept one entry per tool call. That left 724.

How many were real

I drew 50 blocks at random, in proportion to each rule. Claude labelled each one as a real catch or a false alarm, with a one-line reason. I did not re-check the labels.

2 of the 50 were real. One search would have reached a .env.local file and printed secret lines. One command called python3 and would have failed. The other 48 were false alarms. Most of them matched a word like .env inside a search pattern, or a harmless file path held in a variable.

The sample took only one block from each small rule. So it says nothing about force push or a delete of the home folder.

On 10 Nov 2026, a separate code review flagged the variable-path rule too. I narrowed it in my live setup the same day, so it now judges the file name. Every count on this page comes from before that change.

When it broke

  1. 2026-07-11A guard called python3, which this machine does not have. It failed quietly and blocked nothing, for an unknown time.
  2. 2026-07-26The deploy guard blocked every deploy. If Python was missing, it would have let a deploy through.
  3. 2026-07-28The test that proved the deploy guard worked had been saved to a temp folder. It was gone.
  4. 2026-09-14Two hooks were rebuilt but never copied to the backup set. The canary flagged a mismatch at every session start until I found it.
  5. UndatedAn older broken copy replaced a fixed guard. It failed 23 of its own 120 test cases, and nothing reported it. This is the reason the canary exists.

Why it stays private

Before going public, I checked five public projects that guard Claude Code. They already cover the core job, and two of them are widely used. A public copy would add one more of the same thing.

  • destructive_command_guard 6,321 stars
  • cc-safety-net 1,983 stars
  • cc-safe-setup 10 stars
  • arra-safety-hooks 5 stars
  • claude-code-hooks-guardrail-integrity 0 stars

Three parts did not turn up in those five. The canary runs on its own at every session start. A script checks that each rule in my rule table still points at a file that holds it. And a plan has to pass set gates before work starts. Three of the five have a self-check command, but you run it by hand. I only searched these five repos on GitHub, so this does not show the parts are new anywhere else.
